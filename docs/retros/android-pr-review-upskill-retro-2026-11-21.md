### Where the work lost time

| What happened | Lesson |
| --- | --- |
| The first create-rearm test used `runTest`. It passed once, then failed with 923 finalized rows. `runTest` auto-advances virtual time whenever the body waits on Room's real threads, so the idle ticker raced forward. The LLD already warns against unbounded advancing. | A test that mixes virtual time with real threads can pass by luck. Drive a `TestScope` by hand (`runCurrent`, `advanceTimeBy`) and wait on real work in a separate real-time loop. Rerun any new time or concurrency test several times before trusting it, and read the LLD's test-harness paragraph first. |
| The contention test's pause hook fired during setup, because the traced database was already open when the hook was installed. | Arm hooks only when the traced command starts. Clear the trace after setup. Make the hook condition name the command, not just a statement shape. |
| The SQL-trace test passed on the host and failed on API 24. Room nests a `BEGIN`/`END` around each DAO statement, and on API 24 the invalidation tracker ran its own transaction between the two commands, so "transaction number 1" was the wrong one. I ran API 24 only after writing all the tests. | Anything SQL-facing must run on the minimum-API device as soon as it exists, not at the end. Select the transaction by content (the command's gate update and clock read), never by position. |
| Some Gradle runs were piped through `grep` for a few keywords. One run started from the wrong directory and printed nothing useful, so a failed invocation looked like a quiet success until I looked for the result XML. | Never filter build output so that "the build did not run" is indistinguishable from "no matching lines". Always confirm the result files' timestamps and counts, and always run Gradle from the repository root. |
| For the accessible-name finding I assumed the UIAutomator observation would be fixed by a semantics change. After the fix, UIAutomator still showed the clickable wrapper empty, and so did every other Compose button, including ones that already had a content description. The name sat on a sibling node with identical bounds. | Check a control before accepting how a finding frames a platform symptom. Here, the merged-semantics test is the evidence, and the thread reply said so. Do not promise that a platform dump will change when the dump cannot show it. |
| I almost reported "12/24-hour switching verified" after a shell `TIME_SET` broadcast changed nothing. The shell cannot send that protected broadcast. Calling `AlarmManager.setTime` with the *same* time also did nothing; a real delta of a few seconds did produce the system broadcast. | Report only what a check showed. Keep the working technique (alarm service `setTime` with a real delta, and `setTimeZone`) in the device troubleshooting notes. |
| I started a long background Gradle run inside a compound command. The background notification fired when the launcher shell exited, not when the run finished, so it looked like a completed run. | Start long runs with the tool's background option directly, then read the result file. Treat the notification as a launcher event unless the command itself was the long job. |
| The working directory drifted between commands, so some commands failed for path reasons unrelated to the code. | Use absolute paths or a leading `cd` to the repository root in every build command. |
| The user asked for the push and thread resolution only after the commit. That was the right order, but the reply text needs the pushed SHA, and `gh pr view` still reported the old head for a moment after the push. | Push first, then read the head through GraphQL, then post replies that cite the commit. |

### Observations to keep for future PR work

- A review that supplies the reproduction probe and the exact mutation is the cheapest to address: turn the probe into the regression and the mutation into the acceptance check. Without them, write the probe first and watch it fail on the old code before changing anything.
- Proxy assertions (call counts, "the ticker looked again") are useful scaffolding but are the wrong place for a mutation to land. The failing assertion should be the behavior the user or the next subscriber observes.
- A test that shares scenario code across host and device tiers needs its timing to be robust on the slower tier. API 24 on an emulator is the stress case.
- Changing a state model (`CurrentStatus.InProgress`, `StartPreview`) fans out into many tests. Make the model change first, let the compiler list the call sites, then fix the tests in one pass.
- Local review documents and the code commit were intertwined: the review record's resolution table describes code that must already be in history. Commit the code first, then the record.
- Manual device checks are evidence about this build on this emulator. State the device, API level and what was changed, and keep them separate from automated results.
- The transport blocker for backup is a separate fact from the static privacy result. A control package that is itself ineligible proves nothing, so say the control was inconclusive instead of implying the transport is faulty.
- Two emulators plus the managed device ran together without trouble, but start the slow API 24 image early and avoid a Gradle build during its first install.

### Review-to-resolution workflow

1. **Pin the review.** Record base and head, read the approved PRD, architecture, LLD, ADRs, plan, and design, and verify the behavior through production entry points. For each material finding, record the exact contract, observable failure, best diff anchor, and merge impact. Keep the review verdict, GitHub review event, and CI state distinct.
2. **Hand off findings and decisions.** Hand the author the PR and review links, reviewed SHA, stable finding IDs, acceptance tests, still-open evidence, and authorized Git and PR actions. Label creator-owned product choices and engineering decisions explicitly. Apply confirmed amendments to the owning documents under existing approval rules and link them from the durable decision record.
3. **Fix and prove.** Read all review rounds and the current diff before editing. Map multiple threads to their shared fix and keep new scope visible. Reproduce behavior defects on the old code where feasible. For risky rules, use a scratch pass–fail–pass mutation whose red result lands on the behavior assertion. Run the minimum supported device early for SQL and migration changes, and report static privacy configuration, per-package eligibility, and completed transfer evidence separately.
4. **Publish and reconcile.** Carry forward explicit authorization for each action. After an authorized push, read back the PR head and verify it contains the fix commit. Reply using the pushed fix SHA, named test or reproduction, and caveats. Resolve authorized threads when their acceptance criteria are met. Re-read replies and resolution states before updating the durable record and reporting which work is local, committed, pushed, replied to, or resolved. If publication is interrupted, resume by checking current remote state and continue from the missing action.
5. **Re-review the pushed fix when requested.** Verify the affected findings and remaining merge requirements against the current head. A resolved thread records a conversation state. The verifier records whether the issue is independently verified and whether anything still blocks merge. For PR #3, completed device-to-device restore under FR-011 remains unverified even though all 11 threads were resolved.
